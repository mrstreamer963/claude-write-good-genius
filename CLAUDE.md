# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Проект ведётся на русском: документация, комментарии, doc-комментарии и сообщения коммитов —
по-русски; идентификаторы и имена тестов — по-английски. Держись этой конвенции.

## Команды

```bash
make setup   # один раз: rustup target add wasm32-unknown-unknown + npm install
make dev     # собрать WASM и поднять dev-сервер на :5173
make build   # продакшн-сборка (WASM + статика в web/dist)
make wasm    # только пересобрать ядро в web/src/wasm
make help    # список целей
```

Тесты ядра гоняются на хосте (не в wasm), обычным cargo:

```bash
cargo test
cargo test demolish              # по подстроке имени
cargo test whole_room_is_erased_completely -- --nocapture
```

Форматирование — `cargo fmt`. Сборка под wasm требует cfg-флага `getrandom_backend="wasm_js"`
из `.cargo/config.toml` — без него линковка падает; файл не удалять.

⚠️ После `make wasm` под уже запущенным Vite фронт может отдавать старую wasm-обёртку из кэша.
Перезапусти `make dev` (или почисти `web/node_modules/.vite`).

## Архитектура

Три слоя, симуляция авторитетна и детерминирована, JS — «тонкий» вид без игровой логики:

- **`src/`** — ядро по модулям; `lib.rs` держит только крейт-док, сборку модулей и `pub use Sim`.
  Данные: `ruleset` (YAML → структуры) · `map` (тайлы, проходимость, версия) · `path` (BFS) ·
  `components` (компоненты ECS и ресурсы, без поведения). Поведение: `schedule` (цепочка тика) ·
  `jobs` (чертежи) · `hauling` (перенос лома: подвоз на площадку и уборка на склад, работа делится по остатку) ·
  `movement` (шаги, приказы, выход из пустоты) · `demolition` (порядок сноса) ·
  `skills` (навыки: рост от работы, скорость работы, обучение у парты — **приписка, а не
  разовая посадка** (§12.84) — и врождённый предел) ·
  `needs` (усталость: два порога, отдых, переезд упавшего, потолок сна, дремота и
  **ставка расхода по занятию** — §12.99) ·
  `food` (голод: сытость, поход за пайком, вдвое горящая бодрость) ·
  `health` (здоровье: ранение на вылазке, лазарет, работа медика и аптечка-расходник) ·
  `research` (наука: тема, лаборатория, технология) · `timeline` (события по расписанию) ·
  `relay` (дежурство на узле связи: бонус отряду за время связи, **связист садится только по
  приписке игрока** — §12.76 — и **постоянный состав отряда на узле**) ·
  `missions` (вылазки: набор отряда, уход через шлюз, возвращение с добычей, плен и вылазка
  за своим; там же репутация заказчика и пострадавшего — §12.43, **срок из дороги и работы,
  проводник и вилка состава** — §12.70) ·
  `gear` (снаряжение: комплект по шаблону, за которым кот идёт сам) ·
  `crafting` (производство: заказ **в ячейке станка** — §12.96, предмет под ноги,
  **порог автопроизводства** — §12.65, заказывающий порциями на свободные станки — §12.97) ·
  `trade` (внешний рынок: курс по расписанию, сделка в ячейке поста, покупка с доставкой,
  продажа через подвоз и отгрузку — §12.68, **порог автопродажи** — §12.87, правило на предмет
  с названной стороной — §12.88).
  `goals` (цели партии: наблюдатель в конце тика, два вида условий — состояние и журнал) ·
  `save` (сохранение партии: снимок мира, отпечаток рулсета, отладочный журнал команд).
  Наружу: `snapshot` (DTO) · `sim` (`#[wasm_bindgen]`-фасад). Модули приватные, публичен один `Sim`,
  поэтому внутрикрейтовые элементы помечаются `pub(crate)`.
- **`web/src/worker.js`** — WebWorker: фиксированный тик, `BASE_TPS = 6` тиков/сек на ×1,
  скорость (0·1·5·10) = множитель тиков в реальную секунду.
- **`web/src/main.js`** — PixiJS-рендер и ввод. Логики нет, только команды и отрисовка снапшота.
  ⚠️ Панели перерисовываются каждым снапшотом целиком (`innerHTML`), поэтому **кнопки внутри
  них вешаются делегированием на контейнер, один раз** (`onPanelClick`) и ловятся парой
  `mousedown`/`mouseup`, а **не** `click`. Узел кнопки живёт один кадр, а клик человека — сотню
  миллисекунд, и `click` браузер отдаёт ближайшему общему предку, то есть контейнеру: у такого
  события `target` — сам контейнер, и `target.closest('.mission-cancel')` не находит ничего.
  Так дважды умирали «Отменить» у заказа, «Бросить» у темы и «Отозвать» у вылазки: первый раз
  из-за обработчика на самом узле, второй — из-за проверки `target` в делегированном `click`.
  Новая кнопка в панели обязана идти через `onPanelClick`, а не через свой `addEventListener`.
  ⚠️ С §12.71 к ним добавился **штаб вылазок** (`#raidwin`) — модальное окно, где
  состав отряда и карточки заказов стоят рядом. Оно тоже перерисовывается каждым
  снапшотом целиком (в этом весь смысл: щелчок по коту меняет прогноз, и видно
  это сразу), поэтому его кнопки идут тем же `onPanelClick`. Прогноз в нём **весь
  из ядра** (`NodeSnap`: `force`, `forces`, `shares`, `fails`, `spans`, `dangers`,
  `guide`) — считать исход в JS запрещает инвариант 14. Каков **отдельный кот** в
  поле, тоже считает ядро и везёт у самого кота (`EntitySnap`: `raid_force`,
  `guide_step`, `guide_cut`): у узла это знание есть только про уже зачисленных,
  а вопрос «кого добавить» — про остальных. Врождённые параметры в строку не идут
  **ни числом, ни ступенью**: реакция пишется следствием («сложность −34 %»,
  `missions::guide_cut`, выведен из самой `raid_danger`), а выносливость не
  пишется вовсе — на исход она не влияет.
  Список котов в штабе — **четыре группы** (§12.73): идут · в отряде, но
  не пойдут · свободные · в других отрядах. Последняя отделена намеренно:
  свободного кота берут даром, а чужого — отняв его у соседнего отряда, и
  приписка к имени у него — **номер отряда** (`Отряд 2`, порядок `nodes`,
  §12.66), а не координаты рации. Заодно §12.71 запретил
  `disabled` у закрытых кнопок вылазки: по таким элементам браузер не шлёт
  событий мыши, и `title` с причиной отказа не показывается **никогда**. Гасить
  такую кнопку — классом `.tool.off`, а вести ей в штаб, где причина написана
  словом.
  ⚠️ С §12.66 то же верно и для **раздела «Вылазки»** — единственного раздела тулбара, который
  перерисовывается каждым снапшотом (строка на отряд: состав, занятость и таймер меняются).
  Ключ у его кнопок — `data-key` вида `что@x, y`: одна и та же кнопка стоит у каждого отряда,
  и по `data-def` две такие кнопки поделили бы один взвод в `onPanelClick`.
  **Заказов в разделе нет** (§12.75): отправка живёт только в штабе, где рядом состав, прогноз
  и причина отказа словом. Раздел — сводка (кто в отряде, чем занят, сколько осталось) плюс две
  отмены уже принятого решения: «Снять» у правила автовылазки и «Отозвать» у собирающегося
  отряда. Новую кнопку «отправить куда-то» заводить здесь нельзя — она и есть выбор вслепую.
  ⚠️ **В панель клетки (`#cell`) не идёт решение, чью цену она не может показать** (§12.80,
  уточнено §12.95 и §12.96). Кнопок там **две**, и обе проходят по этому правилу, а не в обход
  него. «Пометить на склад»: у пометки цены нет вовсе, она обратима тем же кликом, а что лежит
  на клетке, написано строкой выше. «Отменить» у заказа станка (§12.96): цена написана прямо
  над кнопкой — что делают, сколько осталось и докуда дошла оплаченная штука, — а ключ у заказа
  теперь и есть клетка, потому что заказов на один рецепт бывает несколько и в общем списке три
  строки «Деталь» не различить. Обе — в `KEEPS_CELL`: кнопка стоит в панели той клетки, которую
  сама и меняет, и снятие выделения закрыло бы панель тем же кликом, которым её нажали.
  Всё остальное по-прежнему нельзя, и довод тот же:
  панель отвечает на «что это и что тут сейчас», а решения живут в тулбаре и в штабе. До §12.80
  у рации в ней стоял второй экземпляр списка котов (§12.61) — тот же выбор, но в колонке, где
  не помещается ни исход, ни причина отказа, то есть вслепую; тот же довод, по которому §12.75
  убрала заказы из тулбара. Дорога к отряду одна: клик по рации раскрывает раздел «Вылазки»
  (`cellSection`, §12.55) → строка «Отряд N» → штаб. Панель рации говорит **тремя строками** —
  состав (не идущие тусклым), чем узел занят, есть ли связь; счётчик слотов, роль тайла и
  указатель при набранном отряде выброшены как не про эту клетку. Заодно строка `пусто`
  пишется только на клетках с `capacity`.
  ⚠️ **У торгового поста то же правило, а тикеры и сделки живут в ДВУХ панелях.** Лента
  тикеров (`#tickers`) стоит **первой в правой колонке**, выше всего остального: строка на
  предмет, который игрок сам вынес на главный экран — курс с дельтой, две кнопки сделки и «×»
  (снять тикер; закрепляют его в окне, но гонять игрока туда, чтобы убрать, — дорога в один
  конец). Верх колонки не прихоть вёрстки: панели ниже (заказы, сделки, миссия) появляются и
  пропадают сами, и лента, стоявшая среди них, уезжала из-под курсора между двумя кликами —
  «Продать» второй раз подряд нажать было нельзя. Любая новая панель встаёт **под** лентой.
  Ниже — `#deal`, **плашки сделок**, ровно те, что были до §12.100: `dealGroups` группирует по
  стороне и фракции, и в них только складываемое (§12.83). Панели отвечают на разное, и это не дубль:
  тикер — «почём это сейчас», плашка — «что едет», **включая товар без
  тикера**. Подробностей про одну сделку нет ни в том, ни в другом (§12.82): ни курса, ни срока,
  ни «расчёт через N» — это вопрос к ячейке поста. Кнопки сделки в тикере законны по доводу
  §12.75 («Снять» и «Отозвать» у вылазок): это повторение уже принятого решения, а цена написана
  в той же строке.
  Подробность про **одну** сделку по-прежнему живёт у ячейки: карточка `dealCell` с фракцией,
  разложенной ценой, полоской наполнения и точным сроком. **У мастерской с §12.96 то же деление**:
  панель заказов — сводка без кнопок (сортирована по клетке, как сделки), а карточка `craftCell`
  у ячейки говорит, что за заказ, докуда дошла штука и кто за ним, — и держит «Отменить».
  Делить надо так и дальше: «что у базы есть и какие правила это двигают» — вопрос к окну
  «Склад», «что именно тут стоит, чьё, почём и докуда дошло» — к клетке. Порядок
  карточек держится тем, что `deals` **отсортированы ядром по клетке**: обход ECS зависит от
  истории вставок, и закрывшаяся сделка переставляла бы карточки под курсором.
  ⚠️ **Модальное окно по клику на карте не открывается никогда** (§12.101). Раздел тулбара
  раскрывается **рядом** с панелью клетки (§12.55), а модал накрывает и карту, и саму панель, —
  то есть клик, которым игрок спрашивает «что здесь», стирает ответ. Так на один день попали
  склад и торговый пост, и правило теперь общее: в окно ведут только входы вне карты. Штаб
  вылазок ему не исключение и не был им — туда ведёт строка «Отряд N» в тулбаре.
  С §12.105 к ним прибавилась **мастерская**, но по другой причине: раздела «Производство»
  больше нет вовсе, и `cellSection` по станку не возвращает ничего. Клетка от этого не онемела —
  `craftCell` в панели говорит, что за заказ тут стоит, докуда дошёл и как его отменить, — то
  есть исход ровно тот же, что у склада и поста.
  ⚠️ **Окно «Склад» (`#stockwin`, §12.100) — второй модал, и идиома у него ПРОТИВОПОЛОЖНАЯ
  штабу.** Штаб перерисовывается целиком каждым снапшотом; склад **строится один раз при
  открытии и дальше синхронизируется на месте** (`buildStockWindow` + `syncStockWindow`), как
  тулбар. Иначе в нём молча умирают поля порогов — §12.84, §12.87, §12.89, §12.92, — а
  спасительное сравнение HTML из штаба не сработает ни разу: числа в окне меняются каждым
  кадром. Строка окна — **предмет**: два числа склада (как в шапке, §12.53), «делать до N» по
  рецепту **и рядом с ним кнопка «Произвести»** (§12.65, §12.105; имя рецепта пишется, только
  когда их на предмет больше одного), «сбывать сверх N» (§12.88), **одна сторона на строку**
  (её смена переписывает и порог, и тикер) и курс с дельтой к прошлой фазе. Прогноз вперёд
  в строку не идёт — он в подсказке кнопки, где и жил.
  ⚠️ **Цена рецепта стоит не под кнопкой, а в пустой клетке следующей строки** (§12.105) — той,
  что напротив «сбывать сверх»: своей строкой она растила бы каждую строку рецепта. Есть ли там
  место (следующая **видимая** строка без своей кнопки заказа), решает `syncStockWindow` каждым
  кадром, а не вёрстка: строки прячутся по технологиям и по торговле, и «следующая» меняется от
  кадра к кадру. Места нет — цена встаёт обычным потоком.
  ⚠️ **Что уже заказано, говорит сводка в одной линии с заголовком** (§12.107): «Склад ·
  В работе: Деталь ×12 · Аптечка ×5» — оранжевым названо окно, серым рядом то, что в нём
  идёт; подробности по заказам — в подсказке, своей строки сводка не занимает (заказов нет —
  нет и строки).
  ⚠️ **Подсказка у неё живая (`liveTitle`), и это не украшение** (§12.107): нативный `title`
  браузер рисует **один раз**, в момент показа, — запись в атрибут открытую подсказку не
  перерисовывает, и та, что висит над тикающим числом, врёт («осталось 15» при «×10» рядом).
  Помощник общий: один узел `#livetip` на всё приложение, текст ставится тем же кодом, что
  рисует строку. У элемента с `liveTitle` нативного `title` быть не должно — иначе подсказок
  две. Закрытие окна обязано звать `hideLiveTip`: по удалённому узлу `mouseleave` не приходит.
  Живёт она в окне, потому что панель «Заказы» (`#craft`) **накрыта самим модалом** — то же
  столкновение, из-за которого §12.101 запретил открывать окна кликом по карте; без неё клик по
  «Произвести» не отвечает ничем, ведь запас в строке вырастет через сотни тиков. Складывает она
  `crafting` из снимка (как `dealGroups` — сделки), а состояние заказа называет **одной на оба
  места** функцией `craftStateText`.
  Переключателя у строки два и стоят они врозь: `★` избранное — первым, до названия (порядок
  строк в окне, ворот нет), `◉` тикер — в середине, при выборе стороны (лента на главном экране,
  сторона обязательна). Оба живут **в ядре** (`Favorites`, `Tickers`) и уходят в снимок: зеркало
  в JS уже врало после загрузки у «Убирать сам» (§12.96).
  ⚠️ **У недоступного в окне три состояния, а не два** (§12.100). Технологии нет — не показываем
  **ничего**: правило ещё не механика игры, и полоска «делать до —» обещала бы то, чего в мире
  нет (§12.94). Технология есть, а ячейки нет (`posts`, `shops`) — блок прячется, а причина
  пишется **красным одной строкой в шапке окна**: это чинится стройкой, то есть решением, которое
  игрок может принять сейчас. Есть оба — обычная строка. Порядок проверок значим: сперва
  технология, потом ячейка, — иначе база без мастерской звала бы строить её, ещё не зная
  рецептов. Предупреждение одно на окно, а не по строке на предмет: «нет торгового поста» шесть
  раз подряд — это не шесть новостей (§12.80).
  ⚠️ **У производства видимость кнопки и видимость порога РАСХОДЯТСЯ** (§12.105), и это
  единственное место в окне, где `hidden` висит не на строке, а на трёх элементах внутри неё
  (`−`, подпись, `+`). Строку целиком прячет только отсутствие технологии рецепта. Два других
  условия — про правило и только про него: без технологии автоматики (§12.93) правила нет, а
  руками заказать можно всегда; без мастерской правило не сработает ни разу, но «нет
  мастерской» — это решение, к которому игрок целится, и кнопка остаётся с причиной словом
  (§12.94, `shopsBusyHint` различает «нет мастерской» и «все мастерские заняты»). Свяжи их
  обратно — и кнопка пропадёт у базы, которой всего-то и нужно построить станок. Цена фишками
  стоит **на кнопке**, а не в строке порога, ровно потому, что кнопка живёт дольше полоски.
  Отсюда же и `grid-column: 4` у кнопки в стиле: выпавший из сетки элемент авторазмещение
  ставит в первую колонку, и строка заказа разъехалась бы со строкой сбыта.
  ⚠️ Команда, меняющая мир, уходит через `sendAction` (§12.57): он же снимает выделение
  клетки — но **не выбор котов** (его отпускает повторный клик по коту, а всё разом Escape).
  Осмотр (разделы тулбара, скорость, сохранение) и приказ `move` с карты шлют `postMessage`
  напрямую и выделение не трогают.
- **`assets/rulesets/core.yaml`** — контент в стиле OpenXcom Extended. Лежит вне `web/`;
  Vite раздаёт его через `publicDir: '../assets'` как `/rulesets/core.yaml`.

Протокол `postMessage` (полный снапшот каждый кадр — сознательное упрощение, §12.8a). Палитры
(тайлы, предметы, навыки, параметры, перки, **фракции**, миссии, кандидаты, темы, рецепты) едут
один раз в `ready {meta}`; в снапшоте от них остаются индексы. **Наборы вида
`{имя: сколько}` (цена, добыча, `needs`) приезжают в JS как `Map`, а не как объект** — идиома
чтения одна на всех, см. `costChips` и `trustGap` в `main.js`; `Object.entries` на них молча
вернёт пусто.
⚠️ **Кнопка тулбара, которая меняет свою подпись по снапшоту, обязана делать это только при
изменении** (§12.84): `syncTeachButtons` зовётся каждым кадром, и безусловный `innerHTML`
пересоздаёт детей кнопки каждые 16 мс. Клик человека длится сотни миллисекунд: `mousedown`
приходится на один `<span>`, `mouseup` — на другой, уже несуществующий, и `click` браузер не
выдаёт **вовсе**. Кнопка выглядит живой и молча не работает — на этом умерла «Снять с учёбы».
Это третье лицо тех же граблей, что `onPanelClick`: там узел кнопки живёт один кадр, здесь —
её дети.
⚠️ **Повторяющаяся команда не перечитывает снапшот на каждом повторе** (§12.87): кнопки «−/+»
у порогов (`mkStep`) работают по `mousedown` и разгоняются при удержании, а цель считают
локально — от значения, снятого **в момент нажатия**. Ответ ядра идёт кадр-другой, и повтор,
обогнавший его, послал бы то же число второй раз: игрок держит кнопку, а число стоит. Своего
счётчика, живущего дольше жеста, при этом не заводится (§12.53) — отпустили, и значение снова
из снапшота. Конец жеста ловит **окно, одним слушателем на всё приложение**: тулбар
пересобирается на каждом `ready`, а окно «Склад» — на каждом открытии, и слушатель на каждой
кнопке копился бы с ними.
⚠️ **Пока печатают в поле, клавиши игры молчат** (§12.92): число порога правится на месте
(клик по подписи `.keep-val` → `<input>`), а на окне висят пробел (пауза) и цифры (скорость) —
без проверки `e.target instanceof HTMLInputElement` в начале оконного `keydown` набор «100»
уводил бы партию в ×1. Защита нарочно двойная: у самого поля `stopPropagation` (он же даёт
Escape смысл «отменить правку», а не «сбросить режим»), и общая — на окне, потому что следующее
поле заведут потом и об этом не вспомнят. Подписи, которые зовутся каждым кадром, обязаны
**не трогать** строку в правке (`numEditing`) — иначе снимок затрёт набранное.
⚠️ **И промежуточные значения в ядро не уходят вовсе** (§12.89): число живёт в виде
(`stepEdit`) и уезжает командой, когда набор устоялся (`STEP_SETTLE_MS`). Ядро исполняет
правило сразу, а путь от нуля к тысяче проходит через единицу — «продавать сверх единицы»
выставляет весь склад, и сделку эту не отменить (§12.44). Числа 1, 2, 3 решениями не были,
это механика ввода. Отсюда три обязанности: подпись показывает **набираемое**, а не то, что
знает ядро (единственное место, где вид опережает снимок); переход к другой строке досылает
прежнее число; уход из окна и со вкладки — тоже, иначе набранное не попадёт в автосейв.
Любое будущее правило с числом обязано делать то же.

**Отказ кнопки обязан быть назван словом, и считает его ядро** (§12.53, §12.71): гасить кнопку
`disabled` нельзя — по такому элементу браузер не шлёт событий мыши, и `title` с причиной не
показывается **никогда**; гасят классом `.tool.off`. У сделки причин четыре, и считает их одно
выражение на оба экрана — `tradeState` (§12.100): кнопки стоят и в окне «Склад», и в ленте
тикеров, а лента перерисовывается целиком, то есть своими узлами в `tradeButtons` числиться не
может. Второй экземпляр этой арифметики однажды покажет живую кнопку, которую фасад отклонит.
У обучения (§12.84) причин пять, и две из
них едут числами из ядра: `SkillSnap::desk` (докуда доводит парта **этого** кота — ниже из
потолка парты и врождённого) и `desks` (сколько парт домена есть и сколько свободно; «свободна»
значит «её не держит ничей `Study`» — знание о занятости, которого в виде нет).

**Имущество базы едет разложенным на три числа** (`stock`, §12.53): `stored` (**учтённое** —
склад плюс поднятое с него под сделку; им платят и торгуют, §12.24, §12.69), `loose`
(**неучтённое** — пол и лапы, кроме везомого к посту) и `booked` (обещано покупателю, форма
`owed`, §12.50). Одно общее число обманывало: игрок видел «всё есть», а найм отклонялся.
Груз под сделку числится учтённым **намеренно**: иначе он на время ходки перетекал бы из
главного числа в серое, и оба прыгали бы на каждой ходке. Складывать их обратно в JS нельзя —
считать «чем можно платить» обязано одно место, общее с `plan_spend`.

**Цепочка систем одного тика** (`schedule.rs::build_schedule()`, `.chain()` — порядок значим):
`advance_time → collapse_exhausted → assign_heal → assign_eat → assign_rest → assign_treat →
assign_equip → assign_study → gather_squad → assign_hauls → assign_research → plan_craft → assign_craft → assign_jobs →
mark_loose_scrap → assign_tidy → assign_relay → assign_nap → move_units → work_hauls → work_equip → work_eat → work_jobs →
work_research → work_craft → study → run_missions → run_timeline → run_trade → retry_orders → escape_voids →
spread_units → clear_solids → settle_stacks → sleep → doze → heal → tire → hunger → train_skills →
check_goals`.
Цепочка собирается тремя группами (`assign`, `act` и `settle`) только из-за предела арности
кортежа систем; порядок ровно тот же, что и одним списком.
**Фракции систем не заводят** (§12.43): репутация меняется в единственный момент — на
возвращении отряда, внутри `run_missions`, — как известность, и пустой системы для неё в цепочке
быть не должно.
`run_trade` стоит рядом с `run_missions` и `run_timeline` по той же третьей причине (§12.44):
купленное ложится кучей в ячейку поста, а та могла стать ямой, — съехать на пол оно обязано тем
же тиком. **Деньги за обе сделки считает только `run_trade`** (§12.68): покупка списывается в
фасаде при заказе, продажа начисляется здесь — **разом и по истечении срока отгрузки**, вместе с
журналом `Earned`. До §12.68 продажу капал `work_hauls` поштучно по мере сдачи; переезд убрал
второй счёт, а не завёл его. Коты по-прежнему везут товар обычным подвозом, но доносят они его
**в контейнер** (`Deal::delivered`), а не в кассу.
**`plan_craft` в порядок раздатчиков не входит и котов не трогает** (§12.64): это **правило**, а
не раздача, — оно держит на базе запас, заводя обычный заказ, когда тот просел (§12.65).
**Заказывает оно порциями и на свободный станок** (§12.97): по одному заказу на рецепт за тик,
пять штук или одна, если пятёрка перелетает порог, — теми же двумя размерами, что у кнопки
игрока. Один заказ на всю недостачу (как было до §12.97) занимал бы один станок и **сползался** в
одну ячейку: добор шёл в первую, срез — с последней. Стоит
вплотную перед `assign_craft`, чтобы заведённый заказ получил мастера тем же тиком.
Тесты гоняют ровно эту функцию, поэтому новую систему добавлять только сюда, а не в тестовую копию.
**Автовылазка в цепочку не входит вовсе** (§12.67): `run_auto_raids` стоит в `Sim::tick` **до**
`schedule.run`, потому что повторяет клик игрока по `launch_node`, а тот живёт в фасаде. Система,
делающая то же, стала бы вторым способом уйти в поле — заводить её нельзя.
**Автопродажа стоит там же и рядом** (§12.87): `run_auto_sales` повторяет клик по кнопке
«Продать», а у той трое ворот (свободная **ячейка** поста, прайс фракции, склад минус бронь),
и все три уже посчитаны в `Sim::trade`. Второй их экземпляр открыл бы сделку, **которую нечем
закрыть**: отмены у сделки нет (§12.44). Правило считает ровно одно — размер излишка.
**`check_goals` замыкает цепочку и мир не меняет** (§12.58): цель — наблюдатель, она читает уже
сложившийся тик. Крючков по системам работы у целей нет ни одного и заводить их нельзя.
**Порядок тринадцати раздатчиков = приоритет работ** (§12.15, §12.16, §12.20, §12.26, §12.30,
§12.34, §12.36, §12.37, §12.52): все берут котов из одного пула свободных, поэтому **ранение идёт первым** (§12.37:
остальные решают, чем кот займётся, а этот — что он вообще ничем заняться не может), еда — вторым
(§12.36: ходка за пайком короткая, а сон — сотни тиков, и уснувший голодным просыпается голодным),
отдых — третьим (иначе уставшего кота тут же уводит работа), **лечение — четвёртым** (§12.37:
пациент уже лежит, и каждый тик без медика — это котовремя, которого база лишилась), экипировка —
пятой (§12.34: на базе работа есть всегда, и поставленная после стройки она не случилась бы
никогда), **учёба по приписке к парте — шестой** (§12.84: по тому же доводу, что экипировка, —
приписка, уступающая чертежу, не значит ничего, и выспавшегося ученика уводил бы первый же
подвоз), подвоз на площадки — седьмым (иначе за ломом никто не пойдёт, пока есть обеспеченная
работа), наука — восьмой (за тему уже заплачено образцами, а чертёж на базе есть почти всегда),
производство — девятым (заказ размечен явно и поштучно), стройка и снос — десятыми, уборка пола —
одиннадцатой, **дежурство на узле связи — двенадцатым** (§12.76: раздачи там больше нет — раздатчик
зовёт к рации только приписанного игроком (`Posted`), а место в очереди отвечает лишь за то, что
голод, раны и сон приписку не отменяют; но раз кот сел, чертёж его уже не срывает), а **дремота — последней** (§12.52: она раздаёт не работу, а её отсутствие, и «коту
ничего не досталось» становится фактом только после всех остальных).
`gather_squad` и `study` в этот порядок не входят: они только держат назначенных идущими к
месту. **Раздачи у учёбы нет и с §12.84**: `assign_study` перебирает не свободных котов, а
приписки игрока (`Enrolled`), ровно как `assign_relay` — приписки к рации (§12.76); в общий
порядок он попал только потому, что берёт кота из того же пула. `assign_equip` стоит **перед**
`gather_squad` и единственный берёт кота даже на маршруте, если тот в отряде: сбор ещё не
закончен, а уходить голым мимо лежащего комбинезона — это сила отряда, зависящая от расторопности
игрока (§12.34). `run_missions` стоит после
`move_units` (кот, шагнувший на шлюз, идёт в зачёт сразу) и до `settle_stacks` (добыча ложится на
шлюз, а он мог стать ямой); `study` — там же и по той же причине: кот, дошедший до парты, тикает
в этом же тике.

## Инварианты ядра

Это то, что ломается незаметно и чаще всего:

1. **Проходимость** — только построенный пол (индекс тайла `>= 0`); `-1` = пустота, непроходима,
   пересечь нельзя. Но `find_path` **не требует проходимости стартовой клетки** — на этом свойстве
   держится выход кота из ямы, менять сигнатуру осторожно.
2. **Детерминизм** — фиксированный timestep, фиксированный порядок `DIRS`, никакого рандома и
   wall-clock внутри систем. Любой недетерминизм ломает и тесты, и модель времени (§11).
3. **`BaseMap::version`** — единственный сигнал «карта изменилась»: одновременно гейт для
   `retry_orders` (не гонять BFS каждый тик) и триггер отправки `base_map` в рендер. Тайлы менять
   только через `BaseMap::set`, иначе версия не вырастет и оба механизма молча заглохнут.
4. **Снос идёт от глубины к берегу** (`DemolitionFront`), а не в порядке мазка мыши, и кот работает
   **с соседней клетки** — иначе он сносит пол под собой или отрезает себе доступ к остатку области.
5. **Приказ не срывает кота с начатой стройки**, но кот с *невыполнимым* приказом считается
   свободным для джобов — иначе он никогда не построит тайл, открывающий ему выход из запертой
   комнаты. Это была реальная регрессия; фильтры `Without<Assignment>` / `Without<Path>` в запросах
   `assign_jobs` и `retry_orders` подобраны именно под неё. **Спящего приказ тоже не срывает**,
   пока включено «Беречь себя» (§12.51, инвариант 10): `Order` висит, а маршрут ему проложит
   `retry_orders` в тик пробуждения.
6. **`stuck` — легальное состояние, а не ошибка**: кот замурован в пустоте или его приказ пока
   невыполним. Состояние обратимо (игрок ставит пол рядом) и только подсвечивается в UI.
   **Обратимость держится на `Order::tried_version`, и отмечает она провал, а не попытку.**
   Маршрут теряется не только от непроходимости: его снимают сон, рана и вылазка
   (`release_work`, `release_task`), карта при этом не меняется. Отмечай там попытку — и кот с
   выполнимым приказом остаётся «не может дойти» навсегда, пока кто-нибудь не построит тайл.
   Поэтому `set_target` и `retry_orders` ставят отметку **только на неудаче** и снимают её,
   как только маршрут нашёлся (`an_order_resumes_after_a_nap`).
7. **Занятость кота — это набор фильтров, а не флаг.** Задач уже двенадцать (`Assignment` —
   стройка, `Haul` — перенос, `Rest` — отдых, `Study` — учёба, `Researching` — наука, `Crafting` —
   производство, `Equipping` — поход за снаряжением, `Eating` — поход за едой, `Healing` — лежит
   раненым, `Treating` — лечит раненого, `Squad` — отряд, `OnDuty` — дежурит у рации), и
   каждая новая обязана попасть во все места, где кот считается свободным: `assign_heal`,
   `assign_eat`, `assign_rest`, `assign_treat`, `assign_equip`, `assign_jobs`, `assign_hauls`,
   `assign_research`, `assign_craft`,
   `assign_tidy`, `assign_relay`, `assign_study`, `retry_orders`, `Busy::of` (для `is_stuck` **и** для `job` — того, что игрок
   читает в карточке, §12.41), `spread_units`, `clear_solids`, `doze` (дремота не задача, но
   список «у кота нет ничего» читает целиком, §12.52),
   а также в оба места, где задачу отбирают: `release_task` (приказ игрока, заявка на вылазку) и
   `release_work` (усталость, §12.33; ранение, §12.37). Оба **отпускают, а не гасят claim**
   (§12.48): работу, которую держит claim у самой работы (чертёж, тема, заказ), они очищают явно,
   а подвоз — нет, потому что носильщик записан только у себя.
   Пропущенный `Without<…>` даёт не падение, а тихое перехватывание кота посреди работы или сна.
   Отдельно от них `Away` (кота нет на базе) режет `tire`, `hunger`, `escape_voids`,
   `collapse_exhausted` и рендер. **С §12.40 он стоит и во всех двенадцати раздатчиках**:
   пленный — это `Away` **без** `Squad` (отряд despawn'ится вместе с миссией), и фильтр по
   отряду отдал бы его первому же чертежу. «Нет на базе» — это `Away`, а не `Squad`.
8. **Ничего не остаётся в пустоте.** Кот выходит сам (`escape_voids`), куча лома сдвигается на
   соседний пол (`settle_stacks`, он же сливает две кучи на одной клетке). Правило одно на обоих:
   пустоту не пересечь, значит оставленное в ней недостижимо, — но кот виден флагом `stuck`,
   а лом молча пропал бы (§12.15). Той же природы `spread_units`: **пройти сквозь кота можно,
   остаться в его клетке — нет** (§12.32). Кот не входит в проходимость (иначе маршруты зависели
   бы от того, кто где стоит в этот тик), поэтому правило разбирается после факта, а не запретом
   в семи раздатчиках: остаётся занятый делом, при равенстве — первый по `id`, остальные шагают
   на свободного соседа. **Но выбор места работы занятость всё-таки учитывает** (§12.103):
   `build_spot` — одно выражение на стройку, снос и все три подвоза — ставит клетки, которые
   кто-то держит собой (стоит и никуда не идёт), последними в очереди. Это предпочтение, а не
   запрет: свободной может не быть вовсе. Без него строитель вставал на станок и сгонял мастера,
   а `spread_units` оставлял первого по `id`, а не того, кому клетка нужна. Отряд у шлюза — исключение: сбор по определению сводит котов в одну
   точку (§12.22).
   **Материал тоже не исчезает:** отмена площадки возвращает уже сданное кучей на её клетку
   (§12.31) — в лапах носильщика груз при этом остаётся у него. Той же природы §12.38: **заявка на вылазку
   роняет ношу кучей под ноги коту** — иначе лом уезжает в поле и на сотни тиков выпадает из мира
   (не взять, не разметить). Это единственное исключение из «ношу посреди базы не бросают», и
   граница у него ровная: приказ игрока груз не роняет (кот сходит куда велено и донесёт), а
   вылазка убирает кота с базы надолго. Роняет `Sim::launch` — единственное место, где
   назначается отряд.
   Той же природы `clear_solids` (§12.35): на клетке со свойством `solid` (стеллаж) **пройти
   можно, остаться нельзя**. Проходимость правило не трогает — иначе стеллаж отрезал бы себя от
   носильщиков, которым сдавать груз, стоя на нём; сходят только свободные и спящие, кто при
   деле — остаётся. **Два «после факта» упорядочены между собой** (§12.39): сойти с полки важнее,
   чем не встать вдвоём, поэтому свободного соседа нет — `clear_solids` сходит на занятого
   (наложение разберёт `spread_units`), а сам `spread_units` на заставленную клетку не отходит
   вовсе. Обратный порядок дал бы качели: согнали с полки → развели → загнали обратно.
   **Завал на полу замедляет шаг** тем сильнее, чем куча больше, до потолка
   (`CLUTTER_PER_TICK` / `CLUTTER_MAX` в `movement.rs`), и это второй смысл уборки. Считается
   только пол: сложенное в склад — порядок, а не завал. **BFS о завалах не знает** и не должен:
   он считает шаги, а не время, иначе коты обходили бы кучи, которые сами пришли разбирать, а
   «ближайший кот» в раздатчиках стал бы считаться иначе, чем видно на карте (§11, §12.35).
9. **Навык не влияет на выбор исполнителя, только на скорость работы.** Раздатчики берут
   ближайшего кота (§12.14); мастер на дальнем конце базы вернёт ровно ту беготню через
   полкарты, ради которой §12.14 и писалась. **Ничью «ближайший» не решает, и решать её
   порядком обхода ECS нельзя** (§11, §12.45): он зависит от истории вставок, а у мира,
   поднятого из снимка, она своя. Правило одно на все раздатчики — **коты по `id`, места и
   кучи по клетке**: либо ключ `min_by_key` включает их явно (`assign_equip`, `assign_research`,
   `assign_craft`), либо входные списки сортируются перед жадным перебором (`assign_jobs`,
   `assign_hauls`, `assign_tidy`, `assign_treat`). Новый раздатчик обязан делать то же. Работа считается в **очках**, а не в тиках
   (`BUILD_WORK` / `WORK_RATE`): при `progress += 1` минимальный шаг навыка — двукратное
   ускорение. Новая система работы обязана вешать `Worked(домен)` — иначе навык за неё молча
   не растёт, а начисляет опыт только `train_skills` в конце цепочки (§12.17).
   **Потолок опыта у каждого кота свой** (§12.42): врождённый параметр (`Stats`) режет предел
   уровня в домене — `demands` у навыка задаёт, сколько параметра нужно на 2-й, 3-й, … уровень
   (первый не закрыт **никогда**: список начинается со второго, и «домен недоступен» рулсетом
   невыразимо). Считается это одним местом — `skills::xp_ceiling`, и в него обязаны упираться
   оба источника опыта: работа (`train_skills`) и парта (`desk_cap` = ниже из `taught` и
   врождённого). Разойдись они — кот сидел бы за партой, которая ему ничего не даёт. Параметр
   **не пишет ни одна система**: две шкалы, двигающиеся одним действием, — это один навык под
   двумя именами.
10. **У бодрости два порога, и они забирают кота по-разному** (§12.20, §12.33). Расход за тик
   бодрствования задаёт рулсет, и **ставку выбирает то, чем кот занят** (§12.99): `drain` —
   работа, `walk` — ходьба, `idle` — простой, а **лежащий не тратит вовсе** — и спящий, и
   дремлющий. Ноль в `walk`/`idle` значит «как `drain`», то есть поведение до §12.99, и на этом
   стоят все синтетические схемы. Занятость `tire` разбирает **тем же `Busy::of`, что и подпись
   в карточке** (§12.41): второй перечень задач ради расхода — это тринадцатое место из
   инварианта 7, и §12.52 его уже отверг. Самая дорогая ставка (работа) и есть та, по которой
   считаются сутки (`day = max / drain`, §12.46). **Ступень «Выносливости» вычитается из
   действующей ставки** (§12.70):
   выносливый дольше держится, а не дольше отсыпается, — поэтому пороги остаются абсолютными, а
   сутки считаются одной формулой на всех (`day = max / drain`). Ради этого вычитания шкала
   укрупнена вдесятеро: на «очке за тик» ступень означала бы кратный разброс. Укрупнены **все три**
   шкалы разом (бодрость, сытость, здоровье) — `toll` и `harm` стоят соседними полями одной
   вылазки, и разъехавшиеся единицы там читаются как опечатка балансировщика. Ниже единицы расход
   не опускается никогда: кот, который не устаёт, не уснёт. Выше `tired` кот
   работает; ниже — уходит спать, **но только свободным**: начатое дело обычная усталость не
   срывает, как не срывает его приказ игрока. Ниже `critical` срывает — и **только под свободную
   лежанку**: бросить дело и остаться стоять это ни сна, ни работы. На нуле кота роняет где стоит
   `collapse_exhausted`, откуда угодно и не спрашивая лежанки. Оба срыва **обязаны** явно
   освободить чертёж (`assignee`/`hauler`), пометку кучи, тему, заказ и парту — иначе площадка
   навсегда останется за спящим; поэтому освобождение живёт одной функцией (`release_work`) на
   оба случая. Второй порог выключается игроком (`AutoRest`), и выключение **никого не будит**.
   **Пока `AutoRest` включён, спящего не будит ни заявка на вылазку, ни приказ игрока**
   (§12.51): `Sim::launch` и `Sim::set_target` не зовут на него `release_task` и не трогают
   маршрут — пишут только своё (`Squad`, `Order`), а поведут кота `gather_squad` и
   `retry_orders`, когда он проснётся сам. Решение игрока при этом не теряется и второго клика
   не требует. Это единственные два места, где `AutoRest` читает фасад, а не `assign_rest`.
   `assign_rest` раздаёт лежанки тремя проходами по одному списку свободных мест, в порядке
   нужды: критически уставшие → уставшие → **упавшие** (они уже спят, но на полу — сон там
   вшестеро медленнее, и достроенная зона отдыха обязана их касаться, §12.33). Спать можно на
   любой клетке, лежанка лишь быстрее: скорость сна не бывает нулевой, иначе кот не проснётся.
   **Лежанку занимает один кот** — занятость держит `Rest::spot` спящего (а у упавшего — его
   позиция), поэтому снимается вместе с задачей; свободной нет — кот работает до упора. Делить
   лежанки нельзя: их число тогда ни на что не влияет (§12.20).
   **У сна есть потолок, и он свойство места** (§12.52): `wake` у тайла, `floor_wake` в
   `energy:` для всего остального; ноль значит «до полной». На потолке `sleep` снимает `Rest`,
   и дальше начинается **дремота** — кот лежит там же и добирает бодрость (`doze`), но задачи у
   него нет. Отсюда всё её поведение: её видит любой раздатчик, её не защищает §12.51, лежанку
   она не держит (`assign_rest` считает занятыми только места спящих), а сгоняет дремлющего с
   кровати пришедший спать — обычным `spread_units`. Своего компонента у дремоты нет и заводить
   его нельзя: она и есть «нет задачи + место для сна под лапами».
   К свободной лежанке кота отправляет `assign_nap` — **последний раздатчик** и единственный, кто
   выдаёт не задачу, а маршрут. Идёт кот **по шагу за тик**, а не целым маршрутом: с `Path` он
   невидим раздатчикам (инвариант 5), и дорога через полбазы означала бы простой освободившегося
   чертежа. Занятой при этом считается и клетка под котом, и та, куда кто-то идёт, — иначе двое
   выберут одну лежанку и разойдутся качелями (§12.39).
   **Пошагово идущий останавливается только там, где имеет право стоять** — не на полке (§12.35)
   и не под остановившимся котом (§12.32). Шаг за тик значит остановку на каждой клетке
   маршрута, а обе эти разбираются после факта: замер — согнали — пошёл снова, и коты мечутся
   между стеллажами (реальный баг, §12.52). Поэтому шаг растягивается до ближайшей клетки, где
   замереть можно. Любая будущая пошаговая ходьба обязана делать то же.
11. **Лом не исчезает с пола «в лапы».** Кот поднимает кучу, только если знает, куда её деть, и
   берёт не больше, чем влезет в адресат. Груз в лапах игроку не виден как ресурс и не
   размечается — то, что лежит на полу, всегда можно достать (§12.16). Сумма
   «кучи + лапы + `delivered`» сохраняется; на ней держатся тесты уборки.
   **Отсюда и правило раздачи по остатку** (§12.48): носильщиков у адресата столько, на сколько
   хватает недостачи, но берущий с кучи обязан вычесть чужой груз в пути (`less_incoming`) —
   иначе второй кот поднимет уже везомое, на месте этого никто не ждёт, и лишнее осядет в лапах.
   Из двух промахов лишняя ходка дешевле (§12.15), поэтому место на складе режет уборку заранее,
   а **за какой кучей и за каким типом кот пошёл, записано наводкой** (`Haul::aim`, §12.49) —
   по ней обе раздачи считают обещанное. Наводка **не бронь**: подъём её не читает, кот берёт
   что под ногами, и пропавшая куча остаётся промахом ценой ходки.
   **Единственное место, где предмет законно исчезает из мира, — продажа** (§12.44): товар
   уходит прямо из лап в момент сдачи на шлюзе и **кучей не становится ни на тик**. Это не
   мелочь: `mark_loose_scrap` метит на склад всё, что лежит на клетке без ёмкости, а у шлюза
   ёмкости нет, — полежи проданное хоть тик, уборка увезла бы его обратно. Свойство держит
   ветка `HaulTo::Sale` и тест, проверяющий шлюз на каждом тике.
12. **Тип предмета — индекс палитры `items:`, и он лежит в куче, в грузе и в цене тайла.** Цена —
   **набор** `(предмет, сколько)`, упорядоченный по имени предмета (`BTreeMap` в рулсете): порядок
   доходит до раздачи задач, а `HashMap` сделал бы её недетерминированной. Кот везёт **один тип за
   ходку**, кучи разных типов лежат на одной клетке и не сливаются, а склад типо-агностичен —
   ёмкость считает штуки (§12.21).
13. **Вылазка — единственная работа, где исполнителя выбирает игрок, а не симуляция.** §12.16
   («игрок размечает работу, исполнителя берёт любой свободный») здесь не нарушается, а получает
   границу: раздаётся то, что любой кот сделает одинаково, а от состава отряда зависит исход
   (§12.23). Отряд назначает `Sim::launch` в момент заявки, и **берёт он всех, кто готов**
   (§12.70): спящий (пока включено «Беречь себя»), раненый и не вернувшийся остаются дома, а
   вылазка идёт, если оставшихся хватает на `squad` — минимум вилки. Больше `squad_max` бригада
   не уводит. До §12.70 состав требовался ровно по числу, и один невыносливый кот держал свой
   узел на приколе всё время сна — ожидание это не ротация, а простой. `gather_squad` только
   держит взятых идущими к шлюзу и состав не трогает. **У `launch` двое ворот**
   (§12.43): известность — дорос ли ты вообще, репутация заказчика — станут ли с тобой говорить
   именно эти. Вылазка за своим не закрыта ни теми, ни другими. Шлюз — тайл со свойством
   `gate`, четвёртый случай схемы после `capacity`/`teaches`/`rest` (дальше идут `lab` и `tech`). **Уход — только полным составом взятых**
   (кого взяли, решено в момент клика), таймер идёт с ухода, а не с заявки, и **срок замерзает
   именно там** (§12.70): до ухода `Mission::left` ноль, потому что срок зависит от числа
   дошедших лап. `ticks` у заказа с §12.70 разложен на `travel` (дорога, от состава не зависит) и
   `work` (очки, которые отряд вырабатывает сообща, по очку за тик на лапу) — та же идиома, что
   `BUILD_WORK / WORK_RATE` на базе (инвариант 9), вынесенная за шлюз. **Скорость берётся из числа
   котов, а не из их силы**: считай её силой — и сильный отряд выигрывал бы разом по обоим
   циферблатам. Ушедший отряд не отзывается, и шлюз ему больше
   не пересматривается: коты вернутся туда, откуда ушли, даже если гараж успели снести. **Добыча
   ложится кучей на шлюз**, а не в лапы, — оттуда её разносит обычная уборка (§12.22).
   **Вылазок идёт столько, сколько построено узлов связи** (§12.59): узел — третье применение
   «комната = слот» после мастерской и торгового поста (§12.55) и **единственная чистая
   лицензия**: за ним никто не работает и к нему ничего не возят, он только считается. Пост с
   §12.68 таким быть перестал — он стал местом, куда едет товар. Ноль узлов — ноль вылазок, исключения
   «одна всегда бесплатна» нет. **Двух вылазок по одному заказу не бывает**, и отменяются они
   поэтому **по `def`** (`cancel_mission(def)`), а не по номеру строки: порядок обхода сущностей
   ECS недетерминирован — ровно тот же довод, что у `cancel_craft`. Считают слоты `relay_nodes`
   и `raids_running` в фасаде, наружу едет числом счёт (`relays`), а **ворота — поузлово**
   (`NodeSnap::busy`): глобального «свободен ли хоть один узел» в снимке нет с тех пор, как
   §12.61 сделала кнопку адресуемой узлом, — спрашивают «занят ли **этот**». Второго экземпляра
   этого правила в JS быть не должно. **С §12.61 узел заменяет и выбор отряда**: состав приписан к клетке (`Enlisted`),
   переживает вылазку, и кнопка адресуется узлом (`launch_node`), а не списком котов, — иначе с
   двумя узлами не сказать, чей отряд идёт. Форма та же, что у `Posted`: конфигурация, не задача,
   в фильтрах занятости её нет. Путать с `Squad` нельзя: тот живёт от заявки до возвращения.
   **С §12.67 узел умеет ходить сам**: `AutoRaids` — правило игрока на клетке (заказ на узел, один,
   плюс признак «работает ли оно сейчас» — §12.77),
   и отправляет по нему `run_auto_raids` в фасаде, зовя тот же `launch_node`. Уходит отряд, только
   когда готов целиком (все дома, целы, не спят, не устали): заявка над спящим заняла бы узел на
   всё время сна. Ворот правило не проверяет — они у `launch_at`. Снесённая рация уносит правило.
   **Явный приказ его усыпляет** (§12.72, §12.77): `launch_node` ставит правило узла на паузу, если
   игрок отправил отряд на **другой** заказ; то же делает отзыв собравшегося отряда
   (`cancel_mission`) — иначе «Отозвать» у автоматического отряда не значит ничего, правило заводит
   заявку заново тем же тиком. **Усыпляет, а не стирает**: рутину прерывают ради разового дела на
   базе, и круг после него тот же, — искать тот же заказ среди карточек второй раз значило бы
   принимать решение, которого игрок не менял. Граница — сравнение заказов, а не факт заявки: правило уходит в поле
   через ту же кнопку, но всегда со своим `def`, поэтому снять себя не может, а ручная отправка на
   тот же заказ его не трогает. У вылазки это не расходится с порогом производства (§12.65), где
   ручной заказ порог не трогает: у мастерской правило и приказ живут параллельно, а у узла слот
   один — правило не соседствует с приказом, а отменяет его.
   **С §12.66 узел — ещё и строка в тулбаре**: раздел «Вылазки» это список отрядов, а не список
   заказов, и строка ведёт в штаб, где заказы и стоят (§12.75). Номер отряда — порядок `relay_cells`
   (row-major по карте), своего имени у узла нет: имя это поле в снимке ради подписи.
   **С §12.60 узел не только считается: на нём дежурят.**
   Слот у вылазки именной (`Mission::node`, занимается в момент заявки), а `comms` у тайла —
   второе число той же клетки, как `wake` при `rest`: сколько силы даёт полное дежурство. Ноль
   значит «дежурить незачем», и раздатчик к узлу никого не зовёт — этим же нулём механика
   выключена в синтетических схемах.
   **Но связиста сажает только игрок** (§12.76): `assign_relay` перебирает не свободных котов, а
   приписки (`Posted`), и ведёт каждого ровно на его узел. Пустой эфир — законное состояние:
   вылазка уходит без бонуса связи. Самосева больше нет нигде, поэтому `Posted` — единственная
   причина сидеть у рации, и она же единственный признак «сидит по делу»: снятая или перенесённая
   приписка снимает `OnDuty` тем же тиком. Зеркально к §12.61 («кот числится не более чем в одном
   отряде») **узел держит одного связиста**: новая приписка к той же рации снимает прежнюю молча.
14. **Исход вылазки детерминирован и считается одним выражением — `missions::outcome`.** Сила
   отряда (по коту 1 + уровень «Вылазки» + снаряжение) против `danger`: хватило — вся добыча, не
   хватило — доля, вдвое меньше нужного — провал. **Опасность приходит в `outcome` уже урезанной**
   (§12.70): `missions::raid_danger` делит её на `2 + ступень «Реакции» лучшего в отряде` —
   **проводник**. Форма важнее величины: прибавка к силе линейна и полезна везде одинаково, а
   деление нелинейно и при `danger: 0` не значит ничего, отчего «уборка мусора — справится любой»
   получается даром, без поля «какой параметр меряет заказ». Считается по **максимуму**: сумма дала
   бы квадратичный рост по размеру отряда, среднее наказывало бы за то, что кота взяли с собой
   (реакция врождённа и не растёт, значит «потом» не наступит). Делитель ограничен, поэтому пол —
   свойство формулы, а не отдельная проверка. Броска кубика нет **намеренно** (§12.23): с ним игрок не
   отличит «выбрал слабый отряд» от «не повезло». `outcome` зовут двое — `run_missions` на
   возвращении и `snapshot` для прогноза в панели; развести их значит показать игроку одно, а
   выдать другое. Той же дисциплине подчинены `missions::duration` и `raid_danger` (§12.70): их
   зовут уход и панель, и **прогноз для ещё не начатой вылазки тоже считает ядро** — `NodeSnap`
   везёт `spans`, `dangers`, `ready` и `guide` на каждый узел, потому что цена решения обязана
   быть видна до нажатия, а второй экземпляр выражения в JS обещал бы не то, что игрок получит. `share` мерит **четыре** вещи разом — добычу, известность, раны и репутацию
   (§12.43); пятой арифметики исхода не заводить. Той же дисциплине подчинён `trade::quote`
   (§12.44): цену спрашивают фасад в момент заказа и снапшот для панели, и разойтись им нельзя. Плата за вылазку снимается бодростью **разом на возвращении** (провал — всей):
   в поле кот не устаёт, вылазка считается, а не симулируется.
   **Провал оставляет одного кота в плену** (§12.40) — **первого по `id`**, и это ровно
   детерминизм, а не объяснение. Плен — это `Away` **без** `Squad` и не задача: кот ничего не
   делает и ничего не решает. **Причины плена игра не называет:** ни здоровье, ни навык на выбор
   не влияют, и сверх общих ран пленному не достаётся ничего — «оставили того, кому досталось
   больше» рассказывало бы, что своих раненых бросают. Само время в плену не стоит ничего: там не
   калечат и не лечат, как и в поле (§12.22).
   Две границы держат обратимость и обе живут в `run_missions`: вылазка с `rescue` пленных не
   оставляет **никогда** (иначе спираль), а обычная — только если после этого на базе хватит
   котов на самый маленький доступный спасательный отряд (`rescue_is_possible`, считается **до**
   пленения). `rescue_is_possible` смотрит только на известность и число котов **намеренно**
   (§12.43): она монотонна, а фракционные ворота умеют закрываться — с ними база, рассорившаяся
   со всеми, теряла бы кота навсегда.
   Возвращает пленных успех вылазки с `rescue` — «не провал», без долей: доля меряет
   добычу, а половины кота не бывает. Заявку на неё `Sim::launch` принимает, только пока есть
   кого спасать; самого пленного в отряд не берут — его отсекает та же проверка `Away`, что и
   ушедших.
15. **Известность (`Fame`) — ворота, а не валюта: только растёт и только открывает** (§12.24).
   Даётся той же долей, что и добыча; провал не приносит ничего, но и не отнимает — **ни
   известности, ни репутации** (§12.43): обе расходятся по сделанному. Шкала, которая
   и открывает, и тратится, закрывала бы уже доступное — игрок прочтёт это как баг. Платят за
   найм **предметы со склада**: клетка с `capacity` получает третий смысл после ёмкости и места
   назначения — казна. Котоденьги её **не заменяют** (§12.44): найм, наука и производство
   по-прежнему платят предметами, а деньги живут только на внешнем рынке. Списывается либо весь набор, либо ничего (`spend_from_storage`), а обход
   куч там отсортирован по карте: порядок сущностей ECS зависит от истории вставок и
   недетерминирован.
16. **Обучение адресно, а наука — разметка работы с допуском** (§12.18, §12.25, §12.26).
   Ученика за парту (`teaches` у тайла) сажает игрок — это решение о судьбе конкретного кота, как
   приказ «иди туда», — и с §12.84 это **приписка** (`Enrolled`), а не разовая посадка: сон,
   голод и рана снимают задачу `Study`, но не приписку, и `assign_study` вернёт кота за парту
   сам. Форма и довод те же, что у `Posted` (§12.60), с двумя отличиями: приписка идёт **к
   домену**, а не к клетке (парта — место работы, а не предмет выбора, §12.16), и снимается она
   не только игроком, но и **сама** — по достижении `desk_cap`, иначе доучившийся ходил бы к
   парте вечно. Приказ «иди туда» её **не** снимает, ровно как у `Posted`, и это не симметрия
   ради симметрии: клик по клетке парты — это приказ, и он же то действие, которым игрок
   отправляет кота учиться; снимающий приказ ломал бы механику тем самым кликом, которым её
   включают. Отмена поэтому названная (`unteach`), а не побочная; тему выбирает игрок, а исполнителя берёт симуляция, как у чертежа. Допуск
   («Наука» ниже `level`) **отсекает** исполнителей, и только среди оставшихся работает выбор по
   расстоянию (§12.14) — навык по-прежнему не решает, «кто лучше». Потолок обучения (`taught`)
   живёт у навыка, а не у парты: докуда доучишься — свойство домена. **Парту, как и лежанку,
   занимает один кот** (`Study::spot`), а тема, брошенная приказом или истощением, обязана явно
   очистить `Research::assignee` — иначе она навсегда останется за спящим.
17. **Событие таймлайна — единственное, что происходит без инициатора** (§12.28): не по разметке
   игрока и не по свободному коту, а потому что настал его тик (`at` — номер тика, второго
   календаря нет). У события **два исхода**: успела база к технологиям (`requires`) — груз к
   шлюзу и известность, не успела — `toll` бодрости всем, кто **на базе** (ушедших мир не
   касается, как и усталость). Срабатывает один раз, признак этого — журнал `Chronicle`, который
   только растёт. **Туман предзнания считает ядро**: до `reveal` детали и готовность в снапшот
   не кладутся вовсе.
18. **Три шкалы-ворота, и каждая отвечает на свой вопрос** (§12.24, §12.27, §12.43). Известность
   растёт от вылазок и открывает вылазки и кандидатов — то, что снаружи; технология растёт от
   науки и открывает тайлы палитры (`tech` у тайла) — то, что внутри. Обе отвечают «насколько
   высоко», **только растут и только открывают**. Репутация (`Standing`, по фракции) — третья и
   **единственная знаковая**: она отвечает «от кого» и потому умеет **закрывать**. Честной её
   держат три правила, и работают они только вместе: двигает её **только выполненный заказ**
   (той же долей `share`, что и добычу, — значит провал не двигает вовсе), она **никогда не
   платит** (валюта по-прежнему предметы), и **дорога назад есть всегда** — у каждой фракции
   обязан быть заказ, который она сама не закрывает, а нейтральная вылазка и вылазка за своим
   не закрыты никем. Последнее не украшение: фракционные ворота на `rescue` сделали бы плен
   необратимым (§12.40). Ни одна из трёх не тратится.

   **С §12.93 технология открывает и третье — правила игрока**: порог производства, автовылазку и
   автопродажу. Имена этих технологий живут **в рулсете** (`automation:`), а не в ядре: пусто
   значит «ворот нет», и на этом держатся все синтетические тесты (правила зовутся из 51 места, и
   вшитое в код имя заперло бы их все). Проверяется только **команда** (`set_stock` /
   `set_auto_raid` / `set_sale`) — технологии не забываются (§12.18), значит правило,
   поставленное законно, работать не перестанет, и ни одна система не тронута. **Снятие правила
   ворот не спрашивает**: запертая отмена оставила бы его несбрасываемым. Три флага «открыто ли»
   считает одно место (`Sim::auto_gates_open`), общее со снимком и тестами: снапшот на хосте не
   собрать, а три почти одинаковых поля рядом — приглашение перепутать их местами.

   Ворота тайла проверяются в
   `add_blueprint`, ворота вылазки и найма — в `launch`/`hire`, то есть в момент заявки:
   чертёж или заказ, который никто никогда не возьмёт, читается как поломка. Снос воротами не
   закрыт. Форма правила у вылазки — **`patron` + `against` + одно `standing`**, а не набор
   `(фракция, сколько)`: набором выразим заказ, который нравится всем, то есть фракции без
   решения (§12.43). **Котоденьги (`Money`) в этот список не входят** (§12.44): они и копятся,
   и тратятся, и ничего не открывают — это счёт, а не ворота, и «потратил, теперь не хватает»
   никто багом не назовёт.
19. **Снаряжение — свойство предмета, а надевание — задача** (§12.29, §12.34). `force` у записи
   в `items:` делает предмет надеваемым ровно так же, как `capacity` делает тайл складом; в
   кучах, в лапах и на складе он живёт как лом. Комплект коты добирают сами и **ногами**
   (`assign_equip` + `work_equip`): кот идёт к ближайшей куче — на складе или прямо на полу — и
   берёт вещь оттуда. Мгновенное списание со склада осталось только там, где это **плата**
   (найм, наука, производство): вещь, которая надета, кто-то принёс. Порядок раздачи задан явно,
   по `id` кота: когда комплектов меньше, чем котов, «кому достанется» видно игроку, а обход ECS
   недетерминирован; куча при этом считает, сколько в ней уже обещано идущим — трое за одним
   комбинезоном через полбазы это не «промах ценой ходки» (§12.15), а видимая глупость. Сила надетого входит в **тот же**
   `missions::outcome`, что и прогноз в панели (инвариант 14), а провал вылазки снаряжение
   уничтожает — успех нет.
20. **Производство — первая повторяемая работа** (§12.30). Заказ (`Craft`) — та же разметка
   работы, что чертёж и тема, но со **счётчиком штук**: очереди заказов нет.
   **С §12.102 материал к станку возят ногами, а не списывают со склада**: `Craft::delivered` —
   дословно `Blueprint::delivered`, и адресат подвоза у него свой (`HaulTo::Shop`). Просят
   материал **на всю партию сразу**, а съедают **по штуке**: иначе станок вставал бы после
   каждой и ждал ходку. Берут **откуда угодно, включая пол** — §12.69 разрешает неучтённому
   ровно стройку внутри базы, и производство это внутрь; торговый пост остаётся единственным,
   к кому возят только со склада. Отсюда же и то, что производство **выпало из семи мест,
   читающих бронь**: платы складом у него больше нет, а бронь за него уважает общий подвоз
   (`free_to_spend` — **и в `assign_hauls`, и в `work_hauls`**, §12.106). Заказ без материала не раздаётся и просто ждёт
   (`craft_supplied`, зеркало `missing` у чертежа), а мастер, у которого между штуками кончилось
   привезённое, отпускается на другую работу. **Отмена и снос станка роняют завезённое кучей**
   на его клетку (§12.31, инвариант 8) — до §12.102 возвращать было нечего, и §12.30 называл это
   ценой поспешной разметки. Готовое ложится **кучей под ноги** мастеру.
   Допуска по навыку у производства нет: рецепт открывает технология, «Ремесло» только ускоряет.
   **Заказов идёт столько, сколько мастерских** (§12.55): станок — это слот, и вторая
   мастерская даёт вторую работу, а не декорацию (тот же довод, по которому `capacity` дал
   смысл складской комнате, §12.16). Слот занимает **сам заказ**, а не кот за ним — разметка от
   исполнителя не зависит нигде (§12.16).
   **С §12.96 это буквально: заказ живёт в ячейке станка** (`Craft::cell`, дословно
   `Deal::cell`) — рождается в первой свободной по обходу карты и держит её до последней штуки.
   Ячейку выбирает **ядро**, а не игрок мышью, поэтому отвергнутая §12.55 адресность («заказать
   вот на этом станке») не возвращается, а §12.16 цел. Свободу считает `crafting::free_shop` —
   одно выражение на фасад (`free_shop_cell`), правило и снимок, как `trade::quote`.
   Отсюда всё остальное: **заказов на один рецепт бывает несколько** (пятнадцать деталей на трёх
   станках делаются втрое быстрее, а не по очереди), отдельных ворот «заказов не больше, чем
   мастерских» нет — их заменяет отсутствие свободной ячейки, — а **отменяют по клетке**
   (`cancel_craft(x, y)`), потому что рецепт заказы больше не различает. Свободной ячейки нет —
   штуки добавляются к своему заказу, и на базе с одной мастерской поведение ровно прежнее.
   **С §12.97 правило-порог заказывает порциями, а не ведёт один заказ на всю недостачу**
   (`plan_craft`): по одному заказу на рецепт за тик, `RULE_BATCH` штук или одна, если пятёрка
   перелетает порог, — теми же двумя размерами, что у кнопки. Один большой заказ **сползался** в
   первую ячейку (добор шёл туда, срез — с конца), и три станка снова работали как один; порция не
   растёт, значит копить негде. Отсюда ещё три правила: **уже заказанное идёт в счёт порога**
   (`left` убывает только когда деталь легла под ноги, а материал списан задолго до — иначе
   недостача в штуку даёт по заказу на каждый станок); **сперва рецепты, у которых станка нет
   вовсе** (иначе первый по палитре с вечной недостачей забирает каждый освободившийся станок, и
   остальные пороги не срабатывают никогда); и **ручной заказ идёт в счёт порога, но правилу не
   принадлежит** — срезает оно только свои, поэтому §12.64 больше не нужно пропускать такой рецепт
   целиком. Куда встанет ручной заказ, считает `Sim::spare_shop_cell` — **одно выражение на фасад
   и снимок**, как `free_shop`: свободная ячейка, иначе отобранная у **неоплаченного** заказа
   правила (§12.97). Оплаченный не вытесняется никогда — материал за штуку уже списан.
   **`shop_spot` больше нет**: кот идёт на клетку своего заказа, и пара (кот, заказ) считается по
   расстоянию до неё — дословно `assign_jobs` (§12.14). `assign_craft` раздаёт **списками**:
   `commands` отложены до конца тика, и на втором витке цикла тот же кот выглядел бы свободным.
   Он же убирает заказы снесённых станков: **снесённый станок уносит свой заказ** (§12.96), как
   снесённая рация уносит правило автовылазки. Ячейку при этом **не трогают** `release_work` и
   `release_task` — они отбирают у заказа мастера, а станок принадлежит самому заказу, и снятый
   там он стоил бы заказу оплаченной штуки.
21. **Кот собирается ровно одним `spawn_cat`** — и стартовая тройка из `units:`, и любой новичок
   из `recruits:`. Второе место сборки означало бы кота с лапами другого размера или без
   бодрости, а заметить это можно только по странному поведению. Кандидат уникален и нанимается
   один раз; «уже нанят» спрашивается у самого кота в мире, а не у отдельного списка (§12.24).
22. **У сытости порог один, и цену голода платит бодрость** (§12.36). Ниже `hungry` кот идёт к
   ближайшей куче с едой (`nutrition` у предмета — тот же переключатель, что `force` у
   снаряжения) и съедает штуку **мгновенно по приходу**: вся длительность задачи — дорога, как у
   `Equipping`. Начатое дело голод не срывает, и второго порога у него нет **намеренно**: с
   работы кота уводит бодрость, которая на пустой желудок горит в `starve` раз быстрее (это
   единственное место, где `needs` и `food` пересекаются, — в `tire`). Голод не убивает и не
   калечит: потери котов — отдельный вопрос (§12.5) с отдельной ценой. Сытость тикает **и во
   сне** (время идёт для всех), но спящего голод не будит, а за шлюзом не считается вовсе — как
   и усталость (§12.22).

23. **Здоровье — шкала без таймера, и платит она котовременем** (§12.5, §12.37). Бодрость и
   сытость убывают за каждый прожитый тик; здоровье на базе не убывает вовсе — его роняет только
   вылазка, а возвращает только лечение. Урон считается **той же долей**, что и добыча
   (`harm * (100 - share) / 100`, всё тот же `missions::outcome`): отдельная формула развела бы
   прогноз в панели с результатом (инвариант 14). **Смерти нет:** порог `hurt` выводит кота из
   работы и из отряда, но обратимо. Ранение — единственное, что **срывает начатое** безусловно
   (усталость срывает только под свободную лежанку, §12.33), поэтому обязано пройти через
   `release_work`. Койку (`heal` у тайла) занимает один кот, лежачий переезжает на освободившуюся —
   как спящий на лежанку. **Claim медика чинится в одном месте:** `Healing::medic` снимает только
   `assign_treat`, заметив пропажу `Treating`; все, кто отбирает работу, просто снимают компонент.
   Лечить может любой кот — **допуска у «Медицины» нет** намеренно (в отличие от «Науки»): база,
   где выбывшего некому поднять, это тупик, а не сложность.

24. **Плен — первая потеря, которая сама не проходит** (§12.40, закрывает §12.5). Бодрость
   набегает во сне, раны затягиваются, комплект наберётся заново — а пленный не вернётся никогда,
   пока за ним не сходят: срок ему назначает игрок, а не таймер. Своего таймера у плена нет
   **намеренно**: он был бы первым, тикающим вне базы, и сделал бы цену функцией расторопности
   игрока с секундомером. Цена плена — отнятое котовремя: вылазка за ним. Смерти это не вводит (§12.37),
   поэтому обратимость закрыта **проверкой, а не обещанием** (см. инвариант 14). Наружу плен
   уходит отдельным флагом (`captive` у кота, `rescue` у миссии): пропажа обязана быть объяснима,
   и «ушёл на вылазку» с «остался там» — это разные решения игрока, а не одно состояние `away`.
   **Объяснима — это «его нет и его можно вернуть», а не «вот почему его оставили»:** причины
   плена в игре нет ни в коде, ни в текстах (§12.40).

25. **Котоденьги напечатать нельзя, и в этом вся торговля** (§12.44). Деньги входят единственным
   путём (продажа) и уходят единственным (покупка), поэтому **торговля не создаёт богатства, а
   меняет его состав — и всегда с убытком**: купить дороже, чем продать. Отсюда и то, что она
   не обесценивает ни вылазку, ни мастерскую. Курс — **чистая функция тика** (`trade::quote`):
   фазу выбирает время, значит расписание видно вперёд, и игрок планирует, а не караулит пик с
   секундомером (тот же довод, что у §12.40). **Курс фиксируется в момент заказа** и живёт в
   самой сделке: расписание за время поставки уйдёт, и это риск, а не ошибка. **Сделок идёт
   столько, сколько торговых постов** (§12.55), и **отменить их нельзя** — команды для этого нет
   намеренно, иначе это бесплатный опцион. Ровно поэтому **продать можно только то, что на складе
   есть, и с заявки товар забронирован** (§12.50): слот не отменяется, так что сделка, которой
   нечего везти, заняла бы пост навсегда.
   **Наружу база отдаёт только учтённое** (§12.69): склад минус бронь — то же самое число, каким
   она платит за найм, науку, рецепт и аптечку, и то же, что стоит главным в шапке. Неучтённое
   (пол, лапы, ячейки постов) годится **только на стройку внутри базы**. Граница проходит
   «внутрь/наружу» и держится в голове одной фразой — прежняя («мгновенное списание против
   доставки котами») была верна, но невыразима. Отсюда же **подвоз к посту берёт только со
   складских куч**: ворота, говорящие «с пола нельзя», при котах, несущих с пола, спорили бы с
   картинкой. Пол при этом остаётся законным входом в экономику — потому тупика «склад полон,
   строить нечем» и не возникает. Бронь считается по самой сделке (`trade::booked`),
   своего поля не имеет и снимается сама, а читать её обязаны **все семь мест, где предмет
   уходит с базы**: подвоз на площадку, плата складом (найм, наука, заказ, аптечка), еда,
   снаряжение и **сама заявка на продажу** — она седьмая и самая незаметная, потому что до
   §12.68 её прикрывал единственный слот: с несколькими постами ворота, считающие базу без
   чужой брони, продают один и тот же лом дважды. **Раздача подвоза считает её вместе с
   подъёмом** (§12.106): `assign_hauls` режет недостачу площадки и станка тем же
   `free_to_spend`, что и `work_hauls`, — иначе обещанная ходка снимается тем же тиком, и
   так каждый тик: кот стоит на месте, но занятым числится ровно там, где занятость
   проверяют, и `assign_nap` не уводит его дремать никогда. Продажи срез не касается (бронь
   её собственная), а груз в лапах свободных котов прибавляется обратно — донести его кот
   обязан. Потребности исключением не сделаны:
   проданный паёк коту не еда, а голод не убивает (§12.36).
   **У брони две формы, и путать их нельзя** (§12.50): `trade::owed` — сколько сделки ещё
   должны, `trade::booked` — то же **минус груз в лапах**. Выбор диктует не вкус, а то, что
   спрашивающий считает своим: берёшь **из куч** (подвоз, плата, еда, снаряжение и, с §12.69,
   сама заявка на продажу) — `booked`, потому что из куч лапы уже вычтены; считаешь **добро базы
   вместе с лапами** (`on_base_counts` у порога §12.65) — `owed`, иначе носильщик засчитан
   дважды: раз как «есть на базе», раз как «уже не обещано». Ошибка тихая и в обе стороны: у
   ворот продажи она давала продать ровно то, что кот несёт покупателю (сделка потом висит
   вечно), у порога — перестаёт дозаказывать взамен проданного. С §12.69 у продажи этой развилки
   больше нет: товар уезжает со склада, значит форма всегда `booked`, та же, что у платы. Спред обязан перекрывать и размах фаз, и разницу курсов между фракциями —
   иначе появляется станок; стережёт это `the_shipped_ruleset_leaves_no_arbitrage`, и цифры
   прайса править только вместе с ним.

   **Обе сделки симметричны и живут в ячейке торгового поста** (§12.68). Покупка: деньги
   списываются сразу, через `lead` тиков товар ложится **кучей в ячейку**. Продажа: товар
   бронируется сразу, коты набивают контейнер, и **только с момента, когда он полон**, идёт тот
   же `lead` — по его истечении содержимое уходит, а деньги приходят **разом** (таймер с полноты,
   а не с заявки, — дословно правило вылазки, §12.22). Отдал сейчас, получил потом: до §12.68
   продажа платила поштучно по мере сдачи, и из этой асимметрии росли все неудобства.

   **Ячейка занята сделкой от клика до вывоза, и `capacity` у неё ноль.** Отсюда всё остальное:
   привезённое не оплатит ни найм, ни науку, ни рецепт, ни аптечку (`plan_spend` фильтрует кучи
   по ёмкости клетки, §12.24), в шапке оно едет как `loose`, а уборка увозит его на склад сама.
   Дай ячейке ёмкость — и она станет казной, а вывоз перестанет быть механикой. Свободу считает
   `free_post_cell` в фасаде — **одним выражением на фасад и снапшот**: «сделок меньше, чем
   постов» в JS разошлось бы с ядром на первой же неубранной куче.
   **Содержимое контейнера — счётчик (`Deal::delivered`), а не кучи**: куча на клетке без
   ёмкости тут же поехала бы обратно на склад, и это та же ловушка, что в инварианте 11.

   **Куча в ячейке поста убирается вперёд всех прочих** (§12.98): `free_post_cell` считает
   ячейку с кучей занятой, значит неубранное держит торговый слот, — поэтому у `assign_tidy`
   ключ пары (кот, куча) это `(очередь, расстояние)`, а не расстояние. Внутри очереди §12.14
   цел: у обычных куч цена ходки одинакова.

   Торговый пост с §12.68 — **место, но не рабочее место**: за ним никто не работает, к нему
   только возят, а возить не значит работать; стережёт это `a_post_never_becomes_a_workplace`.
   Счётность осталась прежней (§12.55): второй пост даёт вторую ячейку.

   **У ячейки есть ёмкость** (`lot` у тайла, §12.90): это предел **объёма** одной сделки, общий
   на обе стороны, и берётся он у той клетки, которую сделка займёт (посты бывают разные).
   Ноль — без предела, как и у `capacity`. Без него пост считал бы только число сделок:
   автопродажа (§12.87) грузит весь излишек разом, и одна ячейка вывозила бы сколько угодно —
   второй пост переставал быть решением. **Заявка больше контейнера отклоняется, а не
   срезается** (подменённая сделка необратима, §12.44), а вот **правило грузит по контейнеру**:
   игрок просит конкретную сделку, правило же говорит «сбывай излишек», и партиями оно
   исполняется дословно.

   **Продажу можно поставить на порог** (`Selling`, §12.87): «продавать всё, что сверх N».
   Правило висит на **предмете, а сторона — его поле** (§12.88): адресата называет игрок
   (продавать «кто больше даст» значило бы обыграть его на видимом вперёд расписании и
   торговать с той стороной, от которой он держится подальше, §12.43), но **двух правил на один
   предмет не бывает** — вторая заявка перезаписывает первую вместе с покупателем. На паре
   «фракция + предмет» их выходило по два на лом, и излишек молча доставался первому по
   палитре. Живёт оно в фасаде
   (`run_auto_sales` в `Sim::tick`) и зовёт тот же `trade`, потому что ошибку необратимой сделки
   не откатить. **Излишек меряется складом** (§12.91): `in_storage` минус `booked` — то же
   выражение, которым отвечает `trade`, и одно на оба вопроса («сколько сверх порога» и «сколько
   можно выставить» — это здесь один вопрос). Пол и лапы в порог **не входят**: до §12.91 он
   считал их по аналогии с порогом производства и сливал склад ниже собственного числа —
   правило меряло одним, а тратило другим. С порогом производства это не расходится, а
   дополняет его: тот **кладёт** на базу (готовое ложится под ноги мастеру), этот **снимает** со
   склада, и каждый меряет тот запас, который сам двигает. Уборки за собой у правила нет и быть
   не может — единственное такое правило в проекте.

26. **Снимок покрывает всё, что не правило, и держит это сторож, а не внимательность** (§12.45).
   Сохраняется то, что изменилось с начала партии: карта, девять ресурсов состояния и компоненты
   на сущностях. **Правила не сохраняются** — 14 ресурсов-`*Rules` это разобранный YAML, их
   пересобирает `Sim::new`; сохранить их значит завести второй источник правды рядом с рулсетом.
   Отсюда обязателен **отпечаток рулсета** в файле: индексы палитр лежат в снимке числами, а
   имена — только в YAML, поэтому чужой контент даёт не ошибку, а тихо другой мир; несовпадение —
   явный отказ. Новый компонент обязан попасть в `SAVED` или в `SKIPPED` (с причиной) в
   `src/save.rs` — иначе падает `every_component_is_either_saved_or_skipped`, сверяющий реестр
   `bevy_ecs` с обоими списками **в обе стороны**. Это единственный в проекте случай, когда
   «место, которое нельзя забыть» защищено тестом, а не дисциплиной (ср. инвариант 7), и сделано
   так потому, что забытый компонент здесь **не ломает ничего** — мир после загрузки просто
   немного другой. **Ссылки на сущности** (16 полей: строитель площадки, медик, отряд, куча под
   ногой, адресат подвоза и наводка на кучу) едут номерами и раскладываются вторым проходом —
   `Entity` у нового мира свои.
   Журнал команд (`Trace`) — **отладочный слой, а не источник правды**: партию восстанавливает
   снимок, журнал только объясняет, как игрок сюда пришёл; пишется он в фасаде и нигде больше.
   **Меняешь DTO в `save.rs` — подними `FORMAT` руками:** сторож следит за составом мира, но про
   форму снимка не знает, а `#[serde(default)]` на полях `EntityDto` делает разбор снисходительным,
   и снимок с разъехавшейся схемой загрузится **молча** (пропавшее поле станет `None` — коты,
   например, приедут без бодрости). Это принятая на POC дыра, см. §12.45 и комментарий у `FORMAT`.

27. **Аптечка ускоряет лечение, но не открывает его** (§12.47). `mends` у предмета — тот же
   переключатель-свойство, что `force` и `nutrition`; отдельной сущности у аптечки нет. Платит
   склад **в момент, когда лечение началось** (в `heal`, когда медик дошёл), а не при назначении:
   оплаченное вперёд заморозило бы склад под работу, которая может не начаться (§12.30).
   Тратится **один раз на раненого** — признак этого сам `Healing::kit`, второго флага нет, — и
   прибавка держится до конца лечения, даже если медика увели: трату не отменяют. **Обязательной
   аптечка быть не может:** пустой склад означал бы «раненый не встаёт никогда», то есть тот самый
   тупик, из-за которого §12.37 отказал «Медицине» в допуске.

28. **У цели два вида условий, и путать их нельзя** (§12.58). **Состояние** — каков мир сейчас
   (100 лома на складе); расходуемо. **Журнал** — что случилось хоть раз (сделал аптечку); не
   расходуемо и из состояния не выводится. Правило выбора: **ярлык описывает поступок → условие
   обязано быть журнальным.** Состояние на месте поступка врёт дважды — засчитывает чужое
   («аптечка есть на базе» закроется покупкой на рынке) и не засчитывает своё («денег 50» не
   закроется у того, кто продал на сотню и потратил её). Журналов три (`Raids`, `Crafted`,
   `Earned`), и каждый пишется **ровно в одном месте** — там, где событие происходит
   (`run_missions`, `work_craft`, `run_trade`), по тому же правилу, что и деньги за продажу
   (§12.44); четвёртый обязан заводиться так же. `Goals` **только растёт**: потраченный лом не
   отнимает «Кладовую», поэтому и ярлык пишется в прошедшем смысле, а `hint` — в инфинитиве и
   гаснет при взятии. **Цель — наблюдатель**: `check_goals` замыкает цепочку и мир не меняет,
   крючков по системам работы нет. Скрытая (`hidden`) не идёт в счёт, не держит финал и **не
   уходит в снапшот, пока не взята** (§12.28) — за ней то, чего требовать нельзя: плен случается
   только от провала. Ещё два правила стережёт `every_goal_is_reachable` на боевом рулсете:
   **обязательная цель не выполнима лишь с одной стороны развилки** (§12.43 — иначе одна ветка
   становится единственно верной) и **не выполнена на старте** (на этом уже попалась лежанка:
   стартовая застройка её содержит).

  доступный торговый пост и **непустой контейнер у него** (нулевой означал бы, что предел

  явно (`without_timeline`): мир по расписанию — это шум для чужой механики. Они ловят рассогласование кода и контента (пропавшую
  `capacity`, склад или лежанку без прохода, навык под другим `id`, забытый `carry`, порог сна
  выше потолка, критический порог выше порога усталости или забытый вовсе, **перевёрнутую или
  выключенную нулём лестницу ставок расхода** (§12.99), предмет под
  другим `id`, гараж без `gate`, отряд больше, чем котов на базе,
  **потерянную в стартовой застройке рацию — то есть базу, которая не может выйти на первую
  вылазку, — и случайно размноженную, отнимающую у второго узла смысл (§12.59)**,
  лестницу сложности, где первая вылазка невыполнима, а последняя тривиальна, порог известности,
  до которого не дойти, кандидата с опытом ниже первого порога, класс без парты или с забытым
  `taught`, лабораторию без `lab`, тему с допуском выше потолка обучения, шаблон снаряжения,
  ссылающийся на предмет не тем `id` или на предмет без `force`, мастерскую без `shop` и рецепт,
  закрытый технологией, до которой ему не дожить, вылазку без урона или с уроном, который не
  доводит до порога ранения, лазарет без `heal` или совмещённый со складом, вылазку за своим,
  закрытую известностью или требующую больше котов, чем у базы останется, — то есть плен без
  выхода; фракцию, у которой нет ни одного заказа без `needs`, — из минуса к ней не вернуться,
  первую ступень с заказчиком или полом доверия, вылазку за своим с фракционными воротами —
  то есть плен без выхода вторым путём, `needs` выше `span` — мёртвый контент, и развилку, где
  одна сторона выгоднее другой при том же усилии, то есть выбора нет; прайс, в котором где-то
  купить дешевле, чем где-то продать, — станок для печати денег, обесценивающий всю остальную
  экономику, и ловится он перебором **всех** пар фракций, фаз и при полном доверии обеим
  сторонам), которого синтетические схемы не увидят.
- В схеме `sim_from` тип один — предмет `0`, поэтому `set_cost` задаёт цену именно в нём, а тесты
  типов собирают мир явно (`set_cost_items`, `put_item`).
- Баги здесь живут во взаимодействии систем и ECS-фильтров, а не в отдельных функциях — покрывать
  механику прогоном полной цепочки (`tick_n`), а не юнит-тестом функции.
- Если конечное состояние маскирует ошибку, проверять инвариант **на каждом тике** — как в
  `demolish_job_is_done_from_a_neighbour`, где `escape_voids` иначе замёл бы след.

  Перед изменением поведения симуляции свериться с ним; новое решение дописывать туда же.
  Doc-комментарии в ядре ссылаются на `§12.N` — при правке решения обновлять обе стороны.
- **`concept.md` §11** — техподход, отображение домена на ECS и план POC по шагам (черновой план
  пройден целиком, сверх него закрыты шаги 10–16; из крупного открыты §12.6 и §12.7 — оба
  нарративные и пост-MVP по §10).
- **`ideas.md`** — сырые заметки по сеттингу, **`README.md`** — запуск и известные упрощения каркаса.
- Отдельный слой спек (OpenSpec / Spec Kit) сознательно отложен — см. §12.9 с триггерами возврата.
  Роль спеки исполняет `concept.md`; второй источник правды не заводить.

## Как растить фичи

Правило из §11: новая фича = **компоненты-данные** (`components.rs`) + **отдельная система**
в своём модуле, включённая в `schedule.rs::build_schedule`, минимально трогая существующие. Контент (тайлы, юниты, стартовая застройка) — в YAML, а не в коде; порядок
записей `tiles:` в рулсете = индекс палитры, который потом ходит по всему протоколу и по карте.

**Исключение — шкала-ворота** (§12.43): у `Fame`, `Techs` и `Standing` систем нет и не было
никогда. Системе нужно то, что происходит каждый тик с кем-то, а у этих трёх нет ни
сущности-владельца, ни тиков: только данные, арифметика в момент события и проверка в фасаде.
Пустую систему в цепочку ради симметрии не добавлять. Свой модуль (`src/factions.rs`) фракции
получат вместе с первым поведением по расписанию — когда начнут появляться и исчезать (§4.5).

**Второе исключение — новый адресат подвоза** (§12.44, §12.102): и заказ на продажу, и заказ
мастерской снабжаются ровно как площадка чертежа, поэтому своей раздачи не получили — оба легли
в тот же список `Needy` у `assign_hauls`. Различаются три адресата **ровно двумя вещами**, и обе
живут в типе `Dest`: каким `HaulTo` кончается ходка и можно ли брать с пола. Зато новый адресат
обязан попасть **во все четыре исчерпывающих матча по `HaulTo`**: `components.rs`, `assign_hauls`
(счёт обещанного, вместе с `assign_tidy`), `work_hauls` и `save.rs` (`HaulDto`). Заодно
`assign_hauls` — единственное место, где адресаты **различаются источником**: к площадке и к
станку кот несёт откуда угодно, к посту — только со складской кучи (§12.69). В местах, откуда задачу отбирают, матча больше нет: с §12.48
носильщик нигде не записан, кроме самого кота, и снять с него `Haul` — это всё освобождение.

**Календарь исключение не нужен, потому что он не механика** (§12.46): `day` в рулсете — это
подача, ядро о сутках не знает и ни одна система число не читает. Оно едет в `meta` и
разворачивается в «день 12» на стороне вида; тик остаётся единственными часами мира (§12.28).
Правило общее: то, что умеет влиять на симуляцию, живёт в ядре, а то, что только называет
происходящее словом, — в виде.

**Третье исключение — сохранение** (§12.45): у `save` систем нет и не будет — снимок снимается в
момент события, а не каждый тик. Зато новый компонент или ресурс состояния обязан попасть в
`SAVED` (и в сборку/разбор `save.rs`) либо в `SKIPPED` с причиной — иначе падает сторож
`every_component_is_either_saved_or_skipped`. Ресурс-`*Rules`, собираемый из YAML, всегда идёт в
`SKIPPED`: правила в снимок не сохраняются никогда.

**Четвёртое — правило, повторяющее клик фасада** (§12.67, §12.87): ни у автовылазки, ни у
автопродажи системы нет и быть не должно. Заявка на вылазку — оркестровка на `&mut World`
(`launch_at`), а не изменение данных; система, повторившая бы её, стала бы вторым способом уйти
в поле. У продажи довод другой и сильнее: у `Sim::trade` трое ворот, и разошедшийся второй их
экземпляр открыл бы сделку, которую **нечем закрыть** (§12.44). Оба правила зовут ту же кнопку,
что и игрок, и стоят там же, где стоял бы он, — в `Sim::tick` перед цепочкой. Граница общая:
**правило идёт системой, если ему хватает данных** (как порогу производства), **и зовёт кнопку,
если у кнопки есть ворота**, — тем более такие, чью ошибку не откатить.

**Пятое — цель партии** (§12.58): у неё **одна система, и та наблюдатель**. `check_goals`
замыкает цепочку, мир не меняет и читает уже сложившийся тик — новая цель не добавляет ни системы,
ни крючка, только форму в закрытый словарь `GoalTest`. Крючки по системам работы запрещены: это
десять мест вместо одного, и однажды одно забудут.

Зато **условию-поступку нужен журнал**, и у журнала место записи ровно одно — там, где событие
происходит. Их уже три (`Raids` в `run_missions`, `Crafted` в `work_craft`, `Earned` в
`run_trade` — §12.68), и четвёртый заводится так же: только растёт, идёт в `SAVED`, пишется одной строкой
рядом с самим событием. Правило то же, по которому деньги за продажу считает единственное место
(§12.44). Соблазн взять вместо журнала состояние («предмет есть на базе») — это ровно та ошибка,
из-за которой цель на аптечку закрывалась бы покупкой на рынке.
